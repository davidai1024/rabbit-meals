# 代码导览

## 一张饭桌的边界

`planningFamily` 从微信云函数上下文获取用户身份，关联 `mealIdentities` 和 `mealFamilies`；最多两位成员。角色表示当前协作身份，两人均可切换。

业务读写经云函数校验，不能通过客户端传入别人的 OpenID 或饭桌 ID 绕过成员检查。

## 草稿与已提交菜单

`menu-lifecycle.js` 区分新菜单、重新挑选的替换草稿与显式修改草稿。已提交 `lines` 与 `draftLines` 分开：草稿不进入大厨采购和历史快照。真实变化才撤回旧确认，相同内容重提保留原确认与时间，不重复提醒。

第一道菜标记做好后，客户端与云端同时禁止换菜。共有的 `planning.js`、`menu-lifecycle.js` 在两侧分别保留，修改规则时同步两份实现并运行回归。

## 同步与页面准备

`planning-service.js` 管理串行屏障、版本检查、本机待同步选菜与制作队列。网络错误保留操作；重试前重新校验菜单、饭桌和清空周期，避免旧操作写入新状态。

`pageReady` 与普通写入 `busy` 分开。初次等待身份和数据，已有本次会话缓存时直接显示；后台刷新不反复全屏加载。身份变化先导航到可访问入口，再呈现数据。

## 菜品、照片与提醒

`recipe-catalog.js` 提供原创演示数据。提交保存菜谱快照，后续编辑菜库不会改写历史。公开版图形是本地 SVG，用户上传照片由云函数验证后保存，使用临时读取地址。

菜单和首次点评先落库，再独立尝试提醒。服务端校验订阅偏好、当前成员、消息去重和清空周期，未知发送结果不盲目重发。通知问题不回滚已保存业务。

## 规模与历史兼容

完整饭桌状态存于单个云文档，适合两人轻量使用。长期历史、更多成员或商业场景需自行设计文档拆分、分页、归档与权限边界。`family` 和 legacy fixtures 保留用于旧行为兼容测试，不是新增业务入口。
